# Operation-boundary prior-art check

Inspection date: 2026-10-05. This is a read-only source audit, not a replication or a claim of research priority. No upstream implementation was executed, forked, or copied into the pilot. The following observations refine the candidate in [PROTOCOL.md](PROTOCOL.md).

**Decision:** a bounded dialogue-boundary pilot remains worth designing, but it should be presented as a possible extension of existing retry/reconciliation evaluations. Neither idempotency, replay-versus-new-operation semantics, model-assisted semantic matching, nor duplicate/false-suppression metrics is a new contribution here.

## Cordon: task scope is explicit; adapter not available from inspected links

[Cordon v1](https://arxiv.org/html/2606.17573v1) section 3.1 explicitly separates same-task continuations/retries from new tasks. Sections 4.2 and 5 bind calls to active task context and describe a host bridge that records a task identifier. Section 6 evaluates containment, recovery, and benign task correctness. These sections do not provide a measured dialogue-to-operation-boundary classifier.

The actual outgoing links on the [official project page](https://www.aetherheart.com/en/research/cordon), the paper HTML, and the [first author's homepage](https://zhengchencs.github.io/) were inspected. No Cordon implementation or task-boundary-adapter link was present on those pages. The paper's GitHub links concern cited systems or arXiv tooling. Therefore this audit cannot inspect or reproduce Cordon's concrete task-scope construction. This is a bounded availability observation, not proof that no implementation exists or that Cordon cannot support conversational boundary inference.

## ACRFence: a closer model-assisted precedent

[ACRFence v1](https://arxiv.org/html/2603.20625v1) section 4 already proposes a lightweight analyzer model that compares post-restore tool calls with logged effects, replays semantically equivalent calls, and requires an explicit fork for divergent calls. Section 6 explicitly states that its experiments validate attacks but do not implement/evaluate that analyzer; classifier accuracy and overhead remain future work.

This rules out claiming novelty for using a small model to distinguish replay from a different operation. A possible extension is to measure how dialogue changes intent even when tool payloads remain identical, including legitimate repetitions and clarification. That difference must be tested, not assumed: the paper already recognizes legitimate divergence. A faithful tool-call-comparison baseline inspired by its proposal should be labeled as our operationalization, never an official ACRFence implementation or a reproduction of unavailable analyzer results.

## Consequences for the pilot

1. Keep the scientific target narrow: interpretation of a new user turn before choosing whether to reuse an existing operation identity or allocate another.
2. Preserve stable identifiers and receipts already visible in context. Transport retries with known identities should remain deterministic.
3. Include ordinary instruction models, simple rules with abstention, explicit user choice, and an assisted correct-identity ceiling. A model-assisted tool-call-only comparator is useful as a diagnosed information-limited control, not a fair headline loser when the necessary intent is only in dialogue.
4. Score both unauthorized extra effects and lost legitimate effects, crediting the prior designs. Keep those metrics distinct from unneeded clarification.
5. Do not infer novelty from missing public code or a sparse development split. A promising pilot requires further multi-turn benchmark review and new independent material before a contribution claim.
