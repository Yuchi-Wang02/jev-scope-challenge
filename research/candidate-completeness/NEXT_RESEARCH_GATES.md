# What would justify another study?

Working plan written after the native grids, during the single repaired reasoning
control. These are decision gates and candidate designs, not new frozen datasets,
approved reference labels, completed experiments or promises of novelty.

## Keep the public unit small and complete

The current release can stand on its own: a coverage contrast, all results,
code baselines, exact replay, a failed execution attempt and its repair, and a
neutral review package. Its public question is **"One visible match: when is
caution wrong?"** The substantive claim is the observed explicit-ID deferral
behavior under a declared rubric. Avoid presenting the headline as a general
attack on Jev or as evidence that a different model can replace it.

The original payment pilot stays closed. Its two review submissions are retained
with their scope objection. The new coverage pilot also stops at its fixed arms.
A new cap, another prompt or additional option permutations on the same inputs
would remain development work and would not manufacture independent evidence.

## Three plausible next directions

|Direction|Concrete next deliverable|What would support continuing|What would end or redirect it|
|---|---|---|---|
|Candidate-scoped uncertainty (preferred scientific follow-up)|A new, separately reviewed panel that changes wording and source users, balances decision labels, and crosses request specificity with relevant/irrelevant missing evidence.|The same obligation-specific failure survives ordinary capable baselines, label review and neutral wording without depending on one trigger phrase.|A clear wording repair removes the issue, reviewers reject the semantics, or capable baselines already solve the realistic task. Publish that boundary rather than searching for another failure.|
|Decision audit toolkit (engineering output)|A small reusable CLI that validates choice mappings, effective generation configuration, coverage pairs, retries, stopped runs and reproducible reports. Port only after extracting a stable common interface from the existing studies.|An external user can add a new typed task with independent expected outcomes and reproduce it without editing study-specific code.|It becomes a large generic harness with no real second user/task. Keep the current repo as examples rather than opening empty showcase repositories.|
|Decision sufficiency versus identity sufficiency (higher-risk research proposal)|A precise policy card and finite possible-world examples that distinguish identifying the order from determining a restriction that is invariant across all candidate orders.|Independent reviewers agree on the task semantics and existing work leaves a specific unresolved empirical/method question.|The intended operation requires a unique order by definition, or ordinary code plus a standard resolver already achieves the needed behavior. Do not rename existing uncertainty logic as a new method.|

The last direction intentionally differs from the current unique-target rubric.
For example, uncertainty about which order was intended need not imply uncertainty
about a policy predicate that has the same outcome for every possible target.
Conversely, executing a refund can still require the unique order ID. These are
different interfaces. Any new task must state which one it evaluates **before**
labeling or inference. No present references should be silently changed to fit it.

## A concrete gate before more model calls on a new panel

1. Receive two separate reviews of the present 72 inputs. Preserve submissions,
   exposure/assistance statements and unresolved disagreements. Later review can
   validate a reference interpretation, not turn explored results into confirmation.
2. Identify the unresolved obligation, not just a model with a bad score. For the
   present construction, it is explicit-ID stability under irrelevant-to-identity
   missing candidates. A higher overall score alone does not resolve that question.
3. Write neutral variants without model-output selection. Preserve target, rule,
   payment evidence and coverage semantics; balance grammatical length and remove
   explanations that accidentally instruct a particular answer. Review the variants.
4. Freeze a new source-user split and primary parent-level endpoint. Include both
   answer-changing and answer-preserving pairs, known-grammar code, a scope-blind
   shortcut, constants, and ordinary-model direct plus fixed-budget reasoning.
5. Establish whether a stronger ordinary comparator is available. This machine's
   4B checkpoint and one readout budget do not establish a general-model ceiling.
   Record any new model download, hardware or paid API scope before execution.
6. Use supplied coverage only as a diagnostic. For a deployment-facing claim,
   replace verbal assertions with a documented retrieval contract (query scope,
   pagination/completeness, record identity). A model should not invent those facts.

These are scientific scope gates, not repeated permission requests for already
authorized bounded Jev/local runs. Independent work can continue on methods,
provenance, reusable verification and literature while reviews are pending.

A specific alternative interpretation needs adjudication after the neutral first
reviews: explicit-ID requests also mention a product, while the relevant-omission
premise describes what "a product-name request" does not distinguish. Our labels
interpret that sentence as applying to product-only identification. Reviewers might
read it more broadly. The unique-ID policy supports the intended interpretation,
but code reconstruction cannot settle this linguistic issue. If the text is judged
ambiguous, qualify the affected results and version a wording repair; do not silently
call every deferral a model reasoning defect. The neutral review package does not
preload this hypothesis or model outputs into reviewers' first judgments.

## Where to borrow, and where not to claim novelty

The [post-result primary-source screen](RELATED_WORK_POSTRUN.md) includes prompt
artifacts, evidence-boundary training and agentic stopping. These are direct
precedents for much of the attractive language around this project. Citation is
required even without copying code. Actual code reuse needs pinned versions and
license notices; no additional fork has been created for this pilot.

The useful long-term question remains whether a small model plus explicit software
contracts can deliver reliable decisions at a competitive total cost. A credible
paper needs a contribution beyond a prompt tweak: a validated diagnostic that
changes evaluation practice, a transferable intervention with strong baselines,
or a carefully established replacement boundary. The current 12-parent template
study is an exploratory step toward that decision, not evidence that the gate has
already been met. Hugging Face release and a standalone spin-out follow review,
reuse clarity and external usefulness; stars and deployments are not validation.
